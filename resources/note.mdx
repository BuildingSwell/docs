---
title: "Note"
description: "One rich-text note per deliverable."
---

Each deliverable has at most one note. That makes `deliverableId` the useful key,
not the note's own id.

Standard CRUD applies. See [standard endpoints](/guides/standard-endpoints).

## Fields

Every property the API returns for a note.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | UUID | Unique id. Generated on create unless you supply one. Server-managed. |
| `organizationId` | UUID | Your organization. Taken from the API key, never from the request body. Read-only. |
| `deliverableId` | UUID | Deliverable the note belongs to. **Required on create.** |
| `content` | object | Note body as a rich-text document. This must be a JSON object: a plain string is rejected with `400`. **Required on create.** |
| `createdAt` | date-time | When the record was created. Server-managed. |
| `updatedAt` | date-time | When the record last changed. Server-managed. |

## Write a note without a lookup

Because there is only ever one note per deliverable, `PUT /note/by-deliverable`
creates it if missing and updates it if not. Reach for this instead of `POST`
followed by `PATCH`:

```http
PUT /note/by-deliverable
Content-Type: application/json

{
  "deliverableId": "<uuid>",
  "content": { "type": "doc", "content": [] }
}
```

<Warning>
  `content` must be a JSON object. A plain string is rejected with `400`, so send
  `{ "type": "doc", "content": [] }` rather than `"my note"`.
</Warning>

## What you can write

Everything else in the table above is set by BuildingSwell.

| Field | On create | On update |
| ----- | --------- | --------- |
| `deliverableId` | Required | Yes |
| `content` | Required | Yes |

## Deleting

<Warning>
  **`DELETE /note/{id}` is destructive.**

  Permanently removes the note and its contents. This cannot be undone and there is no archive for notes.
</Warning>

See [archiving and deleting](/guides/archiving-and-deleting) for the full picture across resources.
