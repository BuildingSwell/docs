A comment is one message in a deliverable's channel, optionally with attachments
and optionally as a reply.

Standard CRUD applies. See [standard endpoints](/guides/standard-endpoints).

## Fields

Every property the API returns for a comment.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | UUID | Unique id. Generated on create unless you supply one. Server-managed. |
| `organizationId` | UUID | Your organization. Taken from the API key, never from the request body. Read-only. |
| `channelId` | UUID | Channel the comment belongs to. **Required on create.** |
| `appUserId` | UUID | Author. Defaults to the user behind the API key when you leave it out. |
| `text` | string | Comment body. Up to 50,000 characters. Up to 50,000 characters. **Required on create.** |
| `isEdited` | boolean | `true` once the comment has been edited. Defaults to `false`. |
| `rootDiscussionId` | UUID \| null | Thread this comment belongs to. Shared by every comment in the thread. |
| `replyDiscussionId` | UUID \| null | Exact comment this one replies to. |
| `deletedAt` | date-time \| null | When the comment was soft-deleted. The row is kept as a tombstone so threads and quotes stay readable. |
| `attachments` | object[] | Files attached to the comment. Defaults to an empty list. |
| `createdAt` | date-time | When the record was created. Server-managed. |
| `updatedAt` | date-time | When the record last changed. Server-managed. |

## Threads

Two fields describe a thread, and they answer different questions:

- `rootDiscussionId` is shared by every comment in the thread. Filter on it to
  pull a whole conversation.
- `replyDiscussionId` is the exact comment being replied to. Use it to rebuild the
  reply order inside that conversation.

A top-level comment has both set to `null`.

## Attachments and download links

Each entry in `attachments` carries a `name` and a storage `key`. The `url` is
generated when you read the comment and expires, so treat it as single-use:
download the file or hand the link straight to a browser, and re-read the comment
when you need a fresh one. Store the `key`, never the `url`.

## Deleting a comment

The app soft-deletes: it sets `deletedAt` and keeps the row so threads and quoted
replies stay readable. To match that behavior, patch the field rather than calling
`DELETE`:

```http
PATCH /comment/<id>
{ "deletedAt": "2026-03-01T12:00:00.000Z" }
```

## What you can write

Everything else in the table above is set by BuildingSwell.

| Field | On create | On update |
| ----- | --------- | --------- |
| `channelId` | Required | Yes |
| `appUserId` | Optional | Yes |
| `text` | Required | Yes |
| `isEdited` | Optional | Yes |
| `rootDiscussionId` | Optional | Yes |
| `replyDiscussionId` | Optional | Yes |
| `deletedAt` | Optional | Yes |
| `attachments` | Optional | Yes |

## Deleting

<Warning>
  **`DELETE /comment/{id}` is destructive.**

  Permanently removes the comment row, along with any replies that point at it. This is different from the soft delete the app performs, which sets `deletedAt` and keeps the thread intact. To match the app, `PATCH` `deletedAt` instead.
</Warning>

See [archiving and deleting](/guides/archiving-and-deleting) for the full picture across resources.
