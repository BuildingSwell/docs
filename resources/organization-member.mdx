title: "Users (Organization members)"
description: "User accounts and the roles they carry in your organization."
---

<Note>
  The BuildingSwell app calls this **Users**. The API calls it
  `organization-member`. This page uses the API name so it matches the requests you
  write.
</Note>

A membership joins a user account to your organization and gives it a role. The
account itself is shared across organizations, which is why its email and name
arrive under a nested `appUser` object.

**Search columns:** `appUser.name`, `appUser.email`

<Info>
  Requires admin access, or the `User.Read` and `User.Update` permissions.
</Info>

## Fields

Every property the API returns for a user.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | UUID | Unique id of the membership. Server-managed. |
| `organizationId` | UUID | Your organization. Taken from the API key, never from the request body. Read-only. |
| `appUserId` | UUID | The user account behind this membership. **Required on create.** |
| `roleId` | UUID \| null | Role the user carries. |
| `roleType` | enum | `admin` grants everything. `custom` follows `roleId`. One of `admin` \| `custom`. Defaults to `custom`. |
| `status` | enum | Whether the user can sign in. One of `active` \| `deactivated`. Defaults to `active`. |
| `appUser` | object | Fields joined from the user account. Read-only here, and searchable as `appUser.name` and `appUser.email`. |
| `createdAt` | date-time | When the record was created. Server-managed. |
| `updatedAt` | date-time | When the record last changed. Server-managed. |

## Invite a user

`POST /organization-member` replaces the standard create. You send an email
address, not a user id:

```http
POST /organization-member

{
  "email": "user@example.com",
  "roleId": "<uuid>",
  "roleType": "custom"
}
```

Pass `name` as well to set the display name on a brand-new account.

If no account exists for that email, one is created. Either way an invitation goes
out and `appUser.status` stays `pending` until the person accepts.

Resend it if the first one was missed:

```http
POST /organization-member/<id>/invite/resend
```

## Update a membership

`PATCH /organization-member/{id}` accepts `name`, `roleId`, `roleType`, and
`workerId`. Pass `workerId: null` to unlink the [person](/resources/worker) record.

`name` updates the display name on the linked user account, so one request is
enough to correct a member's name:

```http
PATCH /organization-member/<id>

{ "name": "Jake Smith" }
```

The new name comes back as `appUser.name`, since that is where it lives.

<Warning>
  **`email` cannot be changed.** It identifies the login and is owned by the
  identity provider. Deleting and re-inviting the member creates a *new* account
  rather than moving the existing one, so an email change is a support request.
</Warning>

## Deactivate instead of deleting

Deactivating takes away access but keeps the membership and its history, and it
reverses cleanly:

```http
PATCH /organization-member/<id>/deactivate
PATCH /organization-member/<id>/reactivate
```

Both respond `204` with no body. Reach for these rather than
`DELETE /organization-member/{id}`.

## Two status fields

`status` is the membership: whether the person can use your organization.
`appUser.status` is the account: whether they have accepted their invite and
verified their email. A `pending` account with an `active` membership is someone
who was invited and has not signed in yet.

## What you can write

Everything else in the table above is set by BuildingSwell.

| Field | On create | On update |
| ----- | --------- | --------- |
| `appUserId` | Required | No |
| `name` | Optional, new accounts only | Yes |
| `roleId` | Optional | Yes |
| `roleType` | Optional | Yes |
| `workerId` | No | Yes |
| `status` | Optional | No |

`name` and `workerId` are not membership columns: `name` is written to the linked
user account and read back as `appUser.name`, and `workerId` links the
[person](/resources/worker) record. Neither appears on the membership itself.
`email` is set once, on the invite, and cannot be changed afterwards.

## Deleting

<Warning>
  **`DELETE /organization-member/{id}` is destructive.**

  Permanently removes the membership, which cuts the user's access to your organization. This cannot be undone.

  To take access away reversibly, use `PATCH /organization-member/{id}/deactivate` instead. That keeps the membership and its history, and it can be reversed with `/reactivate`.
</Warning>

See [archiving and deleting](/guides/archiving-and-deleting) for the full picture across resources.
