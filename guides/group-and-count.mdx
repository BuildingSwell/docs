---
title: "Group and count"
description: "Group records by a field and count each group."
---

Group and count answers "how many of each" without pulling the records themselves.
Every resource has it.

```http
POST /deliverable/group-and-count

{ "groupByField": "type" }
```

```json
{
  "values": [
    { "groupId": "phase", "count": 128 },
    { "groupId": "stage", "count": 64 }
  ],
  "hasMore": false
}
```

`groupId` is the value you grouped by, so its type follows the field: a string for
`type`, a UUID for `computed.projectId`, a boolean for `isArchived`.

## Group by more than one field

Pass an array for a compound grouping. `groupId` then holds the combination:

```json
{ "groupByField": ["computed.projectId", "type"] }
```

## Nested paths work

Any path you can filter on, you can group on:

```json
{ "groupByField": "progress.status" }
```

## Array fields need `unnestGroupByField`

Grouping by an array field counts whole arrays by default, which is rarely what you
want. Set `unnestGroupByField` to count each value separately:

```json
{ "groupByField": "computed.tags", "unnestGroupByField": true }
```

Without it, `["urgent", "rework"]` is one group. With it, `urgent` and `rework` each
get their own count, and a record with both tags counts once in each.

## Filters apply

Every filter the list endpoint takes works here too, so you can scope a breakdown
the same way you would scope a query:

```bash
curl -X POST "https://app.buildingswell.com/api/v2/deliverable/group-and-count" \
  -H "X-API-Key: <key>" -H "Content-Type: application/json" \
  -d '{
        "groupByField": "progress.status",
        "filter": "type eq '\''stage'\'' and isArchived eq false"
      }'
```

<Note>
  `groupByField` is required, and it only accepts field-name characters. A value
  with anything else in it is rejected with `400`.
</Note>

## Grouping from a list endpoint

`group-and-count` is the supported way to group, and it is the right tool when you
want counts. List endpoints also accept a `groupBy` parameter, which is what you
need for sums, averages, and other aggregates.

A grouped read must carry a `select` naming the grouped fields and the aggregates
you want, because everything a grouped query returns has to be one or the other:

```bash
# OK — the only selected field is the one being grouped
GET /timesheet?groupBy=workerId&select=workerId

# 400 — no select at all, so every column would come back un-grouped
GET /timesheet?groupBy=workerId

# 400 — startDate is neither grouped nor aggregated
GET /timesheet?groupBy=workerId&select=workerId&select=startDate
```

Aggregates are objects, so they only fit in a `POST /{resource}/query` body:

```json
{
  "groupBy": "workerId",
  "select": ["workerId", { "aggregate": "COUNT", "alias": "sessions" }]
}
```

Each aggregate takes an `aggregate` function, an `alias` to return it under, and a
`field` for every function except `COUNT`. The functions are `COUNT`,
`COUNT_DISTINCT`, `SUM`, `MIN`, `MAX`, and `AVG`.

Two limits are worth knowing before you build on this:

- `groupBy` does not combine with a `join` that selects fields — those come back
  as un-grouped expressions. Group on the resource's own fields instead.
- Some resources always project computed or joined fields, `deliverable` among
  them, so `groupBy` is refused there with a `400`. Use
  `POST /deliverable/group-and-count`, or the domain-aware
  [`POST /deliverable/groups`](/resources/deliverable#group-by-a-domain-dimension).

Each of these is a `400` that names the field or resource at fault.
