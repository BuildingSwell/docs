Every list endpoint takes the same query options, so what you learn here applies to
all of them. `POST /{resource}/query` accepts the same options in the body when your
query is too long for a URL.

## Pagination

```http
GET /project?page=1&pageSize=100
```

- `page` starts at `1`, and defaults to `1`. Pages are 1-based, so `page=0` is
  rejected with a `400`.
- `pageSize` defaults to `100` when you send no pagination parameters at all. Send
  it explicitly rather than relying on the default, which differs between the
  standard endpoints and `/timesheet`.
- The response includes `hasMore`, so page until it is `false` rather than counting
  first.

<Warning>
  `GET /timesheet` applies **no** default page size. Without an explicit `pageSize`
  it returns every matching record in one response and reports `hasMore: false`.
  Always pass `pageSize` there.
</Warning>

## Sorting

```http
GET /project?orderBy=name:asc
GET /project?orderBy[]=name:asc&orderBy[]=createdAt:desc
```

Repeat `orderBy[]` to sort by more than one field, in the order you list them.

## Returning only some fields

Repeat the `select` parameter once per field. A single comma-separated value is
**rejected** with `400` and `Invalid select field: 'id,name'`, so do not reach for
the shorthand:

```http
GET /project?select=id&select=name&select=identifier
```

In a `POST /{resource}/query` body, pass an array instead:

```json
{ "select": ["id", "name", "identifier"] }
```

## Full-text search

```http
GET /project?search=warehouse
GET /project?search=warehouse:name,identifier
```

Append `:column1,column2` to search specific columns. Each resource page lists its
search columns, and searching a resource that has none has no effect.

## Filtering

For simple equality, use the field name directly:

```http
GET /project?name=Warehouse A
GET /deliverable?type=phase&type=route
```

Repeating a field means **any of these values**, so the second example returns both
phases and routes.

Add an operator with a colon:

```http
GET /deliverable?createdAt:gt=2026-01-01
```

| Operator | Meaning |
| -------- | ------- |
| `:eq` | Equals |
| `:ne` | Not equals |
| `:gt` | Greater than |
| `:ge` | Greater than or equal to |
| `:lt` | Less than |
| `:le` | Less than or equal to |
| `:isn` | Is null |
| `:isnn` | Is not null |

<Warning>
  **There is no `:in` operator.** A filter like `progress.status:in=wip,rework` is
  accepted by the parser and then fails at the database with a `500`. To match
  several values, repeat the plain field parameter instead:

  ```http
  GET /deliverable?progress.status=wip&progress.status=rework
  ```
</Warning>

For anything with AND or OR in it, use `filter`:

```http
GET /deliverable?filter=type eq 'phase' and isArchived eq false
GET /deliverable?filter=(type eq 'stage' or type eq 'step') and progress.status ne 'done'
```

Nested paths work in both styles, so `computed.projectId` and `progress.status`
filter the same way a top-level column does.

## Joining related data

Joins let you resolve names in one request instead of following ids around.

```http
GET /deliverable?join:project:id,name=computed.projectId eq relation.id
GET /deliverable?join:project as p:name=computed.projectId eq p.id
```

The format is `?join:<table>:<fields>=<condition>`. Use `relation` to refer to the
joined table when you have not aliased it, or give it an alias with `as` and use
that.

Join on the column the resource actually exposes. A deliverable has no top-level
`projectId`: the project it belongs to is [`computed.projectId`](/resources/deliverable#computed),
and only `order` nodes carry `data.projectId`. Joining a column that does not
exist fails with a `500`.

Three things make joins more capable than they first look:

- Pass several `join:` parameters in one request to join several tables.
- A condition can reference **another join's alias**, not just the base table, so
  you can hop across joined tables in a single request. Declare a join **before**
  any join that references it.
- Conditions support JSONB paths such as `d.data.stageId`, and id fields are cast
  for you.

Chaining is what makes hours reportable. The
[timesheet attribution example](/resources/timesheet#attributing-hours-to-an-order-stage-and-phase)
walks through going from a timesheet row to its order, station, and phase in one
call.

<Warning>
  Joins to internal tables such as `api_key` are blocked.
</Warning>
